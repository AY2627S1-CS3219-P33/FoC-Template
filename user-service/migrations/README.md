# Database migrations

Apply ordered Goose SQL migrations before starting the user service. From
`user-service/`, load the database URL and run:

```sh
set -a
source .env
set +a
GOOSE_DRIVER=postgres GOOSE_DBSTRING="$DATABASE_URL" go run github.com/pressly/goose/v3/cmd/goose@v3.28.0 -dir migrations up
```

For a new database, Goose applies migrations `000001` through the latest
version. Migration files are the source of truth; do not edit migrations that
have been applied to a shared database. Add a new numbered file with
`-- +goose Up` and `-- +goose Down` sections for schema changes.

## Existing database transition

The original migrations `000001` through `000004` were applied manually and
are not recorded in Goose. For a database already at `000004_bootstrap_status`,
record version 4 once before running `goose up`; otherwise Goose will try to
recreate the existing tables. First confirm that `accounts` has the Auth0
identity and no `password_hash`, and that `bootstrap_state` exists. Then run
this SQL once against that database, only if `goose_db_version` does not
already exist:

```sql
CREATE TABLE goose_db_version (
    id integer PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    version_id bigint NOT NULL,
    is_applied boolean NOT NULL,
    tstamp timestamp NOT NULL DEFAULT now()
);

INSERT INTO goose_db_version (version_id, is_applied)
VALUES (0, true), (1, true), (2, true), (3, true), (4, true);
```

Afterward, the `goose up` command above applies version 5. Do not run the
baseline SQL on a fresh database or on a database that already has a Goose
version table. Check `goose status` before and after applying migrations.
If the table was already created with only versions 0 and 4, add the missing
applied history rows for versions 1 through 3 before running `goose up`.

Version 5 stores the original bootstrap Auth0 subject in `bootstrap_state`
and removes `accounts.role`. It preserves account rows and leaves the API's
profile role label derived from Auth0 permissions. The bootstrap subject is
only a durable one-time initialization marker; it does not grant authorization.

Rollback with Goose `down` only after stopping the service. Version 5 can
recreate the role column, defaulting accounts to `USER` and marking the
bootstrap account `SUPER_ADMIN`. Other old local role values cannot be
recovered; Auth0 remains the source of truth. Earlier down migrations may
reject rollback when Auth0-backed account rows exist, and version 1 drops the
account table and all account data.
